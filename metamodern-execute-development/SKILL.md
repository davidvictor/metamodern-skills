# Metamodern: Execute Development

Start from the current request, outcome brief and owning project instructions. Verify actual source, checkout and resource ownership before edits. If the brief is incomplete, resolve only what affects this batch; use `metamodern-plan-development` when available for material reframing. A small clear request does not need a planning stage.

Augment the existing engineering method; keep its mandatory tests, independent review, resource isolation and release controls. Reflect the intended outcome and meaningful assumptions briefly so the user can steer, then proceed under existing authorization.

## Own the outcome

Keep one implementation owner responsible for the batch through investigation, code, focused checks and correction. A clear execution request covers reversible choices within its scope. Continue to the authorized endpoint without repeated permission checks. Ask only for a missing material decision or authority, and keep independent work moving.

Preserve agreed behavior and access, privacy, data-integrity and resource boundaries. Apply authorized replacements directly, including updating obsolete tests and consumers. Add an adapter or abstraction only for a current supported consumer or demonstrated gap. Do not retain abandoned conventions solely because historical tests mention them.

Resolve uncertain migrations through a representative real consumer early. Inspect its rendering and meaningful interaction before multiplying the pattern. Then implement related steps as one coherent delivery batch where project policy allows. Do not turn every family into a separate review, full-suite run or closeout.

Default to sequential delivery worktrees of reviewable size. Complete each batch's required checks, review and authorized delivery before dependent work proceeds; use the verified handoff as its source. Preserve the project's merge authority and dependency contract: an open PR cannot become a merged baseline by assumption. Preparation or read-only research can continue independently. Do not collect several unvalidated changes into a larger batch to save time.

## Keep the loop useful

During edits, run the smallest checks that prove the changed behavior. Distinguish product defects, obsolete assertions, environment failures and unrelated baseline failures from evidence; do not label a failure harmless just because it resembles an old one. Use `metamodern-fix-development` when diagnosis is needed, or the project's repair method.

Review representative visuals and interactions before broad validation. At the integrated candidate run every applicable repository-required check once, in an environment supporting the tested behavior. Track the exact revision and relevant dependency/configuration/fixture inputs. Reuse evidence for unaffected surfaces only when those inputs remain applicable.

Before repeating a check, identify the change or unresolved question and why existing evidence cannot answer it. A runtime correction can invalidate affected checks; a progress message, new chat or unrelated record edit cannot. If required CI repeats a local check, retain both receipts; do not disable CI to save tokens.

After a second same-cause failure without new information, change diagnosis. Repeated freezes, unchanged status turns, mostly obsolete test failures or validation dominating delivery warrant an efficiency checkpoint: narrow the investigation, consolidate remaining work, fix test selection or report a policy conflict. Preserve known material defects until corrected; the checkpoint grants no waiver.

## Delegate and deliver

Delegate only useful independent work or required review, following project model and ownership rules. Send concise source pointers, scope, acceptance and evidence, not the accumulated transcript. Avoid duplicating a worker's investigation. Prefer fresh bounded assignments with a short verified handoff when old histories become irrelevant. Use tools for log comparison and completion waits; report material progress, decisions and blockers rather than unchanged polling.

Use one independent integrated review when required or warranted, through `metamodern-review-development` or the project's canonical reviewer. Group corrections and re-review affected concerns. Follow existing specialist triggers.

Finish the requested endpoint under its actual authority. Record changed behavior, checks, reviewed revision, delivery receipt and limitations. Separate implemented, checked, reviewed, merged, deployed and user-accepted facts. Save enough recovery state to resume without replaying discovery. Report observed token/cost data when requested or diagnosing inefficiency; do not claim savings or billed spend from raw token totals.
