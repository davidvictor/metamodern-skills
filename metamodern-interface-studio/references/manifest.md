# Durable catalog and update contract

## Vocabulary and identity

An **area** groups product work; a **surface** is a renderable primary, detail, overlay, panel, or external place; a **state** names a meaningful condition. A **command** is intent owned by the application, and a **flow** describes a product task. A **fixture** supplies versioned data; a **scenario** selects reproducible state and navigation. A **collection** groups a presenter's selections; a **walkthrough** tells a story through scenarios. Collections need not mirror areas and walkthroughs do not define product flows.

Allocate immutable semantic IDs such as `surface.tasks.detail`, `scenario.tasks.pending`, and `walkthrough.first-task`. Use lowercase dot-separated segments with kebab-case words. Store editable labels separately. Never compute permanent identity from file paths, route strings, order, appearance, or sample people. Versions live in fields, not ordinary IDs. An explicit persistent source annotation or reviewed identity map can establish a rename; path similarity alone cannot.

## Serializable manifest v1

Use JSON or equivalent safe data serialization. This contract defines the v1 fields; project-specific fields belong under `extensions`. Choose actual paths per project. In v1 the directory containing the manifest is the Studio workspace root; every referenced file path is relative to that directory and cannot escape it, including through symlinks. Place the manifest at the shared workspace root when importing local application components. For separate repositories, use versioned source inventories/captures imported into this workspace with repository identity and immutable revision/digest metadata. Direct multi-root resolution needs an explicit schema extension and project validator; the bundled v1 validator does not support it. Never store machine paths or secrets. Rendering functions, closures, runtime handles, stores, timers, and mutable sessions stay in implementation modules outside the manifest.

The manifest contains:

| Field | Contract |
| --- | --- |
| `schemaVersion` | Integer `1`. Unsupported versions open read-only with a diagnostic; do not reinterpret or overwrite. |
| `studioId`, `label` | Stable Studio identity and editable label. |
| `baseline` | `id` content digest, `sourceRevision` (commit or explicit non-Git revision), `dirty` boolean, sorted `files` map of relative paths to SHA-256 content hashes (null means expected absent), `discoveryVersion`, and relevant toolchain/config/lockfile digests. Save the normalized source inventory with this baseline, including missing files. |
| `records` | Array of generated catalog records defined below. Records are uniquely identified across kinds. |
| `overlaysFile` | Presenter-owned serializable records and field overrides keyed by stable IDs; includes collections, walkthroughs, narration, decisions, labels, and review context. |
| `baselineFile` | Last accepted unoverlaid source projection G and source inventory, immutable for a given digest; never the merged effective records. The referenced file is `{schemaVersion: 1, records: [...], inventory: {...}}`. Enables three-way reconciliation with current editable Studio files. |
| `conflictsFile` | Persistent unresolved conflicts and reviewed resolutions; may be an empty array file. |
| `evidenceFile` | Verification and capture records; append only when an actual check or capture occurs. |

A catalog record has `id`, `kind`, `label`, `lifecycle` (`active` or `removed`), `owner` (`generated`), `sources`, `dependencies`, `statuses`, and `data`. `sources` is an array of `{path, export, route, targetId, digest}` with non-applicable fields explicitly null. Routes are mappings, never identity. `dependencies` contains stable record IDs plus source-file dependencies in the `data.sourceDependencies` path-to-digest map where needed. Statuses are independent `design` (`unknown`, `exploration`, `selected`, `approved`), `delivery` (`unknown`, `concept`, `prototype`, `implemented`, `deployed`), and `evidence` (`unverified`, `source-checked`, `runtime-checked`, `user-accepted`), each represented as `{value, evidenceId}`. Use null evidence for unknown/unverified states; substantive claims require a reference to an evidence record. Never upgrade these fields from recency or a passing unrelated test.

Required kind-specific `data`:

- `area`, `state`, `command`, `flow`, `anchor`: semantic description; flows reference commands/surfaces, anchors name meaningful focus or assertion points. Commands reference the application-owned implementation.
- `surface`: `areaId`, `surfaceKind`, `targetIds`, `stateIds`, source component/export and route mappings in `sources`.
- `token`: semantic meaning, source symbol/key, resolved values by applicable target/variant/theme, source dependency digests, and consumer surface IDs. Record missing/unresolved values rather than guessing equivalence.
- `target`: platform, adapter module reference, supported combinations, and per-preview capability/fidelity declarations per [adapters](adapters.md). Capabilities can be narrowed by a scenario; never expand beyond runtime negotiation.
- `profile`: `targetId`, viewport width/height/scale, orientation, input methods, safe areas, system appearance and reduced-motion setting.
- `variant`, `theme`, `revision`, `condition`: meaning, applicable targets and resolver/implementation references. Keep these separate axes. Conditions specify controlled network/environment outcomes.
- `fixture`: `version`, `file`, `digest`, `provenance` (`origin`: `synthetic`, `licensed`, or `approved`, plus `author` or `rightsReference`), `audiences` (explicit permitted audience IDs), and redaction/expiry restrictions if any. A changed payload requires a new version. Publish resolves the actual fixture file and audience policy, not just its label.
- `scenario`: `fixtureId`, `fixtureVersion`, `stateId`, `targetIds`, fixed ISO `logicalTime`, `seed`, `conditionIds`, navigation snapshot, `setupCommands` (ordered), `completionSchedule` (controlled async outcomes) and `assertions` arrays. Large payloads belong in versioned referenced files whose digests participate in fingerprints. See [scenarios](scenarios.md).

Historical tombstone sources and dependencies describe the last observed source and need not exist on disk today; validate their shape without executing them. Historical evidence may reference tombstones, but evidence cited for current claims must resolve against current records. Use typed references (`areaId`, `scenarioId`, etc.) and explicit dependency arrays; do not hide references in prose. A reference to a missing record is invalid. A reference to a tombstone is **unresolved**, not valid simply because the ID still exists. Removed records retain their original ID, last sources, `removedAtBaseline`, and reason; exclude them from runnable discovery but show them wherever presenter work still references them. Never reuse a removed ID for another concept.

## Presenter overlays and evidence

The overlay file has its own `schemaVersion: 1`, `overrides` keyed by record ID and field path, and presenter `records` with IDs/kinds `collection`, `walkthrough`, `comparison`, or `decision`. The shape is `overrides[recordId][fieldPath] = {value, baseValue}` or `{value, baseHash}`; the base is the generated value/hash it was authored against. Presenter-owned entries use `{id, kind, label, lifecycle, owner: "presenter", data}` and reference catalog IDs. Collection data contains `scenarioIds`; walkthrough data contains ordered `steps`, each with `scenarioId` and optional `anchorId`, narration, commands, expected outcomes and timing. Comparison data contains `axis`, `values`, and fixed selection inputs; decision data contains author, scope, date, evidence and subject IDs. Their lifecycle, narration, order, selections, and decisions are never regenerated from source. Orphaned overrides are retained and flagged. The v1 override allowlist is `label`, `data.description` (both nonempty text), and `data.reviewContext` (typed references checked). Store narration, walkthroughs, collections and decisions in presenter records. Reject aggregate `data` replacements and all other override paths; they could otherwise replace source-owned capabilities or references. Direct edits already present in generated records are still preserved/reconciled through C in the three-way merge. Overrides cannot change identity, lie about capabilities, or grant source approval.

Walkthrough/collection/comparison fields follow [presentation](presentation.md). Store long narration and media outside the catalog with content digests. Decisions cite their author, scope, date, and evidence; recording a presenter decision does not change product approval status.

Both the conflicts and evidence files use `{schemaVersion: 1, records: [...]}`. Evidence records include ID, check kind, outcome (`passed`, `failed`, `unavailable`, `stale`), environment/tool versions, target/profile, scenario and fixture version, input fingerprint, source baseline and dependency hashes, adapter version/fidelity, variant/theme/revision, capture path/hash and time when applicable, and limitations. The pre-capture freshness key hashes this explicit input tuple: source baseline and transitive dependency digests, adapter/build/toolchain version, target/profile, scenario/fixture version and digest, materialized fingerprint, command-history digest if modified, variant/theme/revision, logical clock, seed, conditions, locale/time zone and capture settings. Outcome, capture time, artifact path/hash and limitations are result metadata, not key inputs. Changed source, dependent tokens/assets, fixtures, adapter/config, or presentation inputs make matching prior captures stale. Unknown dependency coverage means freshness is unknown, not current. Preserve historic evidence; compute current freshness from inputs.

## Concrete three-way Update

Inputs: **B** = last accepted generated baseline; **S** = inventory of current application source; **C** = current Studio generated records plus presenter overlays. Produce **G** by projecting S through the same discovery rules and identity map. Do not alter the application.

1. Snapshot/hash B, S, C and presenter files before planning. If B is missing, inspect/adopt current Studio ownership explicitly; never assume existing files are disposable. Read current state before retrying an interrupted write.
2. Match records by established stable identity. Explicit rename mapping preserves IDs and updates source/route/label mappings. Ambiguous one-to-many or many-to-one matches create deterministic conflict IDs from competing IDs and content hashes; retain prior identity pending resolution. New unrelated records get new IDs. Deletions create tombstones, not cascading deletions.
3. Merge each generated field with a missing-value sentinel distinct from null: if C equals B, take G; if G equals B, preserve C; if C equals G, keep it; otherwise preserve C and record `{recordId, field, base, current, incoming, sourceBaseline, status: unresolved}`. Treat a modified record versus source deletion as a conflict and preserve its edited content in a removed tombstone. Arrays with ordered meaning are atomic unless they have stable element IDs and a defined order merge.
4. Leave presenter files byte-for-byte unchanged unless this operation specifically requests presenter edits. If a generated base underneath an override changed to a different value, keep the override, expose the new base and an overlay conflict. Revalidate every collection, walkthrough, comparison and decision reference; record broken references and stale anchors explicitly. Do not rewrite the story to fit available surfaces.
5. Compute transitive token/source dependency drift and invalidate affected evidence. Review the proposed patch and conflicts. Build a candidate snapshot; validate schema, typed references, fixture versions, ownership, supported target/profile combinations, and runtime checks appropriate to changed seams. An unresolved story can remain visible, but cannot claim a passing resolved walkthrough or silently run.
6. Commit a generation atomically: write candidate files and its inventory/baseline to a new directory, verify hashes, then replace a small current-generation pointer. Recheck the input hashes immediately before switching; concurrent edits abort the switch. Keep the prior generation until the new one reads back successfully. Small single-file implementations can use temp-file plus atomic rename and a backup; multi-file updates need a pointer or journal to avoid mixed baselines.
7. Save the incoming unoverlaid source projection G as the next merge ancestor, separately from the merged effective records. For example, when C differs from B but G equals B, retain C while keeping G as ancestor; the next unchanged Update must retain C again. Advance the accepted source baseline only for recorded source observations; retain each unresolved conflict's original base/current/incoming values across later updates. Do not treat the newly saved baseline as resolution. Source equality may deduplicate a conflict, never erase it. Resolve only with an explicit reviewed mapping or field choice recorded with provenance.

Canonical serialization sorts unordered maps/sets, preserves meaningful array order, and excludes changing run timestamps from semantic output. Unchanged inputs plus unresolved conflicts produce the same files and conflict IDs; do not append identical diagnostics or refresh capture timestamps. A no-op Update writes nothing.

## Recovery and migrations

For a known older schema, make a backup and run a deterministic named migration on a copy; preserve IDs, ownership, tombstones, manual files, conflicts and evidence provenance. Validate and test the migrated result before the atomic switch. Never auto-downgrade a newer schema or discard unknown fields; refuse mutation and report the required reader/migration. Migration fixtures must include presenter edits and a failing case. Schema v1 has no implicit legacy migration.

After interruption, the last valid generation pointer remains authoritative. Verify staged hashes and current input hashes before resuming; otherwise retain the old generation and discard only the unreferenced candidate created by this operation. Surface stale source or pending update state in the Studio. Recovery cannot truthfully mark stale previews current. Conflicts block affected previews/publication claims, not unrelated read-only inspection.

## Proportionate automation

Use `node scripts/validate-manifest.mjs path/to/manifest.json` from this skill for the common v1 integrity checks documented in its output. It is read-only, checks referenced data, and exits nonzero for malformed or unresolved material. It does not discover arbitrary frameworks, merge files, prove component exports/routes exist at runtime, establish permissions, or verify visual fidelity. Extend project tests for those seams rather than adding a generic workflow engine.
