# Studio shell

Read this for Build, and for any Update or Verify that touches the Studio's own interface. The shell is the Studio's own product: a calibrated grey stage, an icon rail with contextual panels, and five views. It has its own visual language, separate from every product it presents, and it never renders product UI itself. Previews reach it only through the [frame protocol](frame-protocol.md) or as recorded captures.

The starter in [assets/studio-shell](../assets/studio-shell/README.md) implements everything below and runs a synthetic example product live. Start every new Studio from it rather than from a blank project or from another product's Studio.

## Start a Studio

1. Inspect the application first (see [SKILL.md](../SKILL.md)). Decide the target, fidelity and preview strategy before copying anything.
2. Create the Studio with `node scripts/update-studio.mjs <dir> --create` from this skill, in the location the user chose. A folder inside the product repository, such as `studio/`, keeps the adapter next to the source it describes; a separate repository needs pinned source imports as described in [manifest.md](manifest.md). The command copies the starter without `node_modules` or `dist` and writes `studio-shell.lock.json`, which later shell updates need (see [updating.md](updating.md)).
3. Run `npm install` and `npm run dev` and confirm the example runs before changing anything. This separates shell problems from integration problems.
4. Write the product adapter in `src/adapters/`, generated from the manifest and runtime catalog, and point `src/adapter.ts` at it. The adapter is data: IDs, labels, axes, capabilities, scenarios, walkthroughs and tokens. It never contains rendering code.
5. Build the product's preview entry with `connectStudioFrame` and set the adapter's `frameEntry`, or supply captures for a capture-only Studio. Follow [web.md](web.md) or [native.md](native.md) for the boundary.
6. Set the title, output folder and extra pages in `studio.config.ts`, and reduce `src/adapter.ts` to the product adapter. These two files belong to the product; the rest of the starter belongs to the shell and is replaced by updates, so product needs never go there. The acceptance suite measures the shell with the example product: keep `example/`, `src/adapters/example.ts`, `src/adapters/synthetic.ts` and `scripts/acceptance.mjs` together to keep it runnable, or delete them together, remove the example from `studio.config.ts`, and record them with the updater's `--removed`.
7. Verify with the acceptance criteria below and [verification.md](verification.md).

Product development chrome that would sit inside every preview (a "development preview" strip, a role picker, links back to a catalogue) belongs to the Studio, not the frame: replace it in the frame build with an empty substitute, declare it as a presentation override, and move any control it carried into a dock input. Never edit the product's source to do this.

Change shell components only to fix a shell defect or to meet a criterion here. Product needs belong in the adapter: an extra scenario input, a named variant axis, a presentation override. If a product seems to need a shell change, record why in the Studio's notes and keep the change product-neutral.

## Layout

| Region | Rule |
| --- | --- |
| Rail | 48 px, always visible above phone width, never collapses. The product mark (the adapter's `product.markSvg` paths, drawn in white on a solid brand tile in both appearances, else its two letters), then the five views as square, full-width items with tooltips and number keys, then, when the adapter declares a workspace, a divider and its modules (icon, label under, tooltip; see [workspace](workspace.md)), then, when the adapter declares a library, another divider and the library's one item (see [library](library.md)), then Go to and Keyboard shortcuts at the foot. The active view has a straight 2 px brand marker on the left edge and a filled background; focus is an inset square outline. The active label uses `--rail-active` and reaches 4.5:1 in both appearances. No rounded rail items. Modules and the library item use the views' marker, filled background and inset focus outline. |
| Context panel | 272 px beside the rail, content follows the view: catalog for Inspect and Compare, filters for Gallery, the step list for Present, and for Design the Adjust parameters or the token families. Clicking the active view again hides it. It has no close button of its own. The catalog and step list are windowed lists with one tab stop, so size does not change their cost. For an open workspace module: its sections, then the module's optional Panel. For the library: its components under their group headings, with search. |
| Panel toggle | One control: the button at the left of the top bar, whose icon shows what it will do, plus ⌘B and the full-height sidebar edge. Never two controls for the same action side by side. |
| Top bar | Panel toggle, breadcrumb (product, view, scenario, where the scenario opens Go to; or product, module, section for a workspace module; or product, library, group, component on a library page), live status, then Go to, Studio settings, Studio appearance, Copy link and the Details toggle. The breadcrumb truncates before anything overlaps it. Edited and a fidelity badge show only in bars at least 576 px wide (both are always in Details). On a phone, and on a touch screen whose bar is narrower than 576 px (such as a tablet with a panel open), the four actions fold behind one trigger that slides them out to its left (inert while folded, Esc or a choice folds them); fine pointers never fold. The product mark's tile stays square. |
| Stage | A neutral grey surface with a faint 24 px grid: lighter than the Studio in light appearance, darker in dark. The preview sits centered with nothing drawn above it. Fidelity is stated in Details (summary and Fidelity tab); a static capture or recreation also shows its fidelity badge in a top bar at least 576 px wide. Scale is stated by the dock's Zoom control ("Fit · 54%"), and by a size chip under the frame in views without a dock. The frame's outer line is a quiet hairline (at most 20% black in light); the corner ticks carry the edge at 3:1. An open workspace module's page sits on the Studio surface instead; product output inside a module uses the kit's PreviewFrame on the stage surface. A library page is one documentation column on the Studio surface, with its previews on the stage surface inside each preview block. |
| Stage navigation | The same on every stage that shows frames at a scale (Inspect, Compare, Design, Responsive row and canvas): scroll or a two-finger swipe pans, and over a frame the page scrolls first and the stage takes what the page cannot use; ⌘ or Ctrl with the wheel, or a pinch, zooms around the pointer, over frames too, from 10% to 400%; Space and a drag, or a middle-button drag, pans (a shield covers the frames while Space is held; in Compare, Space flips the sides, so only the middle drag); + and − step the zoom, ⇧1 fits and ⇧0 is 100%. The zoom menu names the gestures in one line. |
| Dock | Floating under the preview: theme, the Design menu, size, any dock inputs the scenario uses (such as Role), zoom, Product back, Reset. These change how the scenario is viewed, not what it is. When themes pair with high-contrast versions (`contrastOf`), the theme buttons are the standard themes and Contrast is in the Design menu, with the dock inputs in the `design` group (such as density) and a way into the Design view. When the dock is wider than the stage it wraps onto another row instead of scrolling, so every control stays on screen. |
| Details | 320 px on the right, docked, pushing the stage. Summary always visible (position in the catalog, area, title, description, fidelity, status and Edited), then Scenario, Fidelity and Evidence as line tabs, and Code in Inspect when the scenario has properties and its frame announces `code`. Scenario inputs live here because they change what the scenario is; so do component properties, which edit the selected state (see Properties and saved states). On Design's Tokens tab it becomes the token editor. For an open workspace module it shows the module's Details, and is hidden when the module has none. On a library page it shows On this page, the playground and the preview theme. |

Below 1280 px only one side panel stays open: the one just opened wins. Below 768 px the rail becomes a bottom bar with Panel, the five views and Details, each entry at least 44 px and as wide as its label needs; the panel and Details open as swipeable drawers; the dock becomes a full-width strip; fit means fit to width and the stage scrolls; a phone profile opens by default when the product declares one, unless the adapter names a `defaultProfile`, which opens on every screen size. With a workspace declared, a Workspace entry takes Details' place in the bottom bar and opens a drawer of modules, and Details moves to the top bar. With a library declared, the Workspace drawer lists the library after its modules; in a Studio with a library and no workspace, the library's entry takes Details' place instead.

On a coarse pointer, at any width, every Studio target is at least 44 px (a switch, checkbox, radio or slider thumb by its hit area) and text fields use 16 px text; the shell keys this off `pointer: coarse` (`useCoarse` in `src/hooks/use-mobile.ts`), not the width. The 44 px is the area a finger can actually reach, not only the box: stacked switches, checkboxes and list rows with a button sit 44 px apart, or the whole row is the control's label, so no hit area overlaps the next one or slides under the panel's edge handle, and a slider's marks sit clear of its thumb. Two narrow pointer conveniences are equivalent-control allowances rather than targets: the panel's edge handle, whose 44 px equivalent is the top bar's Hide panel (or Show panel), and the frames' resize grips, whose equivalents are the dock's Size menu in Inspect and the width list and custom size in Responsive. Keyboard focus on buttons, links, tabs, rows, options, menu items and switches draws one 2 px outline in `--ring` (inside the item for rows, tree items, options, menu items, tabs, tab panels, the breadcrumb and the rail, where a clipping ancestor or a scroller would cut it; around the thumb, 2 px out, for a slider, whose focus sits on its hidden range input), at 3:1 or more in both appearances and in `Highlight` under forced colors, and never clipped to less than its perimeter; text fields keep their focus border.

Per-viewer layout settings live in Studio settings: presentation controls as a dock or a stage toolbar, Details docked or floating, labels under rail icons. Defaults are dock, docked and labels under the rail icons on desktop. Switch to the toolbar when a product declares more than four presentation axes.

## Views

| View | Contract |
| --- | --- |
| Inspect | One scenario in its own runtime with live status, reset, product back and scenario inputs. With a live frame and `axes.resizable`, the frame has right, bottom and corner drag handles: the edge follows the pointer, a size readout names a profile it lands on, edges are drawn to profile sizes and adapter breakpoints unless Shift is held, the scale is frozen during the drag and refits on release, and the frame is never remounted. The handles are also sliders (arrow keys 1 px, Shift 10 px), a double-click returns to the profile's size, and the size travels in the link as `size=WxH`. Releasing on exactly a profile's size selects that profile. |
| Compare | One changing axis, two sides, each its own runtime. The axis is Theme, Profile, any scenario input the adapter declares, or a property whose control is `switch`, `select`, `choice` or `presets`, or `range` or `number` with presets (never text or readonly); each side carries every other input and property edit the viewer chose, and a property axis sets that property on its side only, never in the Inspect edits. Side by side, Split (a handle on the seam, arrow keys in 5% steps; disabled with a reason on the Profile axis, where the sides differ in size) and Flip (Space). Nothing is shown while the pair is healthy; interacting with one side shows a warning with Reset both, until the sides match again. Details and the status follow the pair (Loading, Ready, Modified), never a previous view's state. A side's header is as wide as its preview, and at least 60 px so Reset's target fits: it wraps, a long value name truncates with its full name as its title, and below 7rem the status shows only its dot or icon, keeping its word as its accessible name, so no header leaves the stage and nothing spills out of a header. Saved comparisons name their axis. |
| Responsive | The scenario at several sizes, each frame its own runtime. Presets (the adapter's `axes.responsive.presets` first, then Phones; Phone, tablet, laptop; and Desktops) and layouts saved in the Studio's `layouts.json` (`studio-layouts/1`, a product file) are listed in the panel. Frames are added from the profiles, the adapter's and the shell's devices, or a typed size (a size outside the profiles needs `axes.resizable`), removed, reordered in the Frames list with Alt and an arrow key, resized with the Inspect handles, reset one at a time or all together, and opened in Inspect; at most six. **Row** shows them at one shared scale (never above 100%, stopping at 20% and scrolling inside the stage), each labeled with its size and the profile it counts as. Dragging a frame's label, or Alt and an arrow on it (8 px, 64 with Shift), places it anywhere: the others stay put, the zoom holds, the stage grows to reach every frame, and the places are kept in the viewer's browser and the link (and saved with the layout). An icon in the Responsive toolbar puts the frames back in a row. Resize handles hug each frame and keep their size on screen at any zoom. **Full page** grows each frame to its content (up to 16,384 px) and says when a page sizes itself to the window instead. **Canvas** (React Flow, loaded only when opened) places frames freely: pan by dragging empty canvas, Space and drag, a middle drag, or scrolling (over a frame too, once its page is at its end); zoom from 10% to 400% at the pointer, with the dock's zoom control; labels stay readable outside the zoom and are the only drag handle; 8 px snapping, arrow keys, multi-select, Tidy in the toolbar and a minimap from the zoom menu (off by default); switching from the row keeps every frame where it was, and a canvas opened with neither a saved viewport nor a row opens with every frame in view; positions and the viewport are saved. **Sync** (all on for a new layout) repeats scrolling, clicks and typing, and navigation across frames; a frame that cannot follow says Out of sync, and one whose client cannot sync says Not synced. Only the dev server writes `layouts.json`; a published Studio reads it. Unsaved edits stay in the viewer's browser and travel in the link. Property edits apply to every frame. On a phone frames stack. |
| Gallery | Grouped by area with search, area filters and a flagged-only switch. Captures when recorded; live thumbnails mount only while near the viewport and are not interactive. A card opens its declared scenario in Inspect. Gallery shows named states only, saved states included, never unsaved property edits. |
| Present | The walkthrough player from [presentation.md](presentation.md). Steps replay their commands through the frame before ready. A missing scenario, a Later surface, a failed command or a missing anchor stops the step with the reason and a Skip action; nothing is substituted. Up to 24 steps show as progress segments; beyond that one bar with marks for broken steps, a step count, and an All steps list. Touching the preview pauses and offers Restore this step. Exit returns focus to what opened Present. The narration bar lays out by its own width: one column below 576 px, then two columns with the controls on a row beneath, and three columns from 896 px, so text and controls never overlap. Present plays named states and step values, never unsaved property edits, and mounts a fresh runtime for every step, so two steps on one scenario that differ only in values never share product state. |
| Design | Shown when the adapter declares `design` parameters or a token source; Adjust and Tokens are tabs over one draft layer, and old `view=tokens` links open the Tokens tab. **Adjust** turns the parameters into draft token values, CSS rules and font stylesheets: sliders for scale, ratio and temperature (with marks at the modes the product ships, which a click selects), a typeface from a list or any Google Font name, and colors. A list says what the values change (for example "Density 0.90× changes 26 tokens"), which tokens are missing from the source, which fixed values will not follow, and warnings for small text and low contrast. The stage shows As built, Draft or both side by side, with a Draft design badge and a hold-to-see-as-built button, and a type specimen beside the screen. The draft reaches the live frame without a remount and travels in the link. **Tokens** is the token table: product tokens only, both theme columns, each value drawn on the product's own ground, with family, flag and search filters, a windowed grid grouped by family whose families over 60 start folded; drafts are edited one token at a time in Details and validated, and a hand-edited token wins over what Adjust generates. Below 1024 px the table stacks over the stage and each row puts its Light and Dark values under the name, up to two lines each, with the full value in the tooltip. A per-viewer switch, off by default, shows the draft in Inspect, Gallery and Compare, always badged; Compare then offers a Design axis (As built against Draft). Present never shows a draft. Save as variant downloads a variant file (token overrides per appearance, with any CSS and fonts) for the Studio's variants folder, and Export downloads the draft as a CSS or JSON token diff with from and to values: a proposal, never a decision. |

The skill's four required views remain Inspect, Compare, Gallery and Present. Responsive is always offered; Design appears when the product declares design parameters or has a token source.

## Tokens of the shell

The shell uses shadcn's semantic tokens (background, foreground, muted, border, ring, sidebar) and adds a small set in `src/studio.css`.

| Token | Role |
| --- | --- |
| `--stage` | The grey surround: light in light appearance, dark in dark. Its text and the corner ticks keep 4.5:1 and 3:1 against it in both, and the two keylines keep any product edge at 3:1 whichever it is. |
| `--boundary-inner`, `--boundary`, `--tick` | Two keylines and corner ticks. In light appearance the keylines are white then dark and any product edge reaches 3:1 against one of them. In dark appearance the inner keyline is a faint white hairline (a solid white ring read as a heavy border): the corner ticks carry the 3:1 boundary and the hairline keeps a near-black or stage-matching product edge from being lost. |
| `--anchor` | Walkthrough highlight, drawn by the shell over the frame with the anchor's name in `--anchor-foreground` (white in light, near-black on the lifted dark anchor, 4.5:1 or more in both). The name sits above the highlight when the frame has room, below it when not, and inside its top edge when neither fits; it runs from the highlight's edge toward the frame's far edge and truncates there, so it never leaves the frame. It takes no pointer, so its full name stays in its text (after a visually hidden "Highlighted:") for assistive technology. In forced colors the highlight is a 2 px `Highlight` outline and the name a `Canvas` and `CanvasText` pair. |
| `--success`, `--warning`, `--info`, `--danger` and their `-surface` pairs | Ready, modified or stale, draft or simulated, unresolved or failed. |
| `--fidelity-static` | Static captures. |
| `--dock-shadow`, `--ease-out-quint` | Floating surfaces and panel motion. |
| `--rail-active` | The active rail item's label: the sidebar primary in light, lifted halfway to white in dark, so it reaches 4.5:1 in both. |

The light `--ring` and `--sidebar-ring` are OKLCH lightness 0.556, so focus outlines reach 3:1 on the Studio's light grounds.

Shell tokens never reach a preview, and product tokens never style the shell, even where names match. Product theme and Studio appearance are independent. Anything the Studio changes about product rendering, such as a forced font, is an adapter-declared presentation override listed in Details under Fidelity.

## Brand color

Neutral by default; an adapter can start on its product brand with `product.brandDefault`, and a viewer's own choice, including Neutral, still wins and is remembered. Studio settings offers the product's brand (from the adapter), five presets and any CSS color. It sets `--primary`, `--ring`, `--sidebar-primary` and `--sidebar-ring` with a foreground chosen for 4.5:1 contrast; in dark appearance the color is lifted to at least OKLCH lightness 0.72, and in light appearance the ring, the sidebar ring and `--rail-active` use it lowered to at most lightness 0.5, so a pale brand still gives 3:1 focus outlines and a 4.5:1 active rail label while fills keep the brand itself. It tints primary buttons, switches, focus rings, the rail marker and the mark. The stage, preview boundary, status and fidelity colors never change. It is stored per viewer and per Studio.

## Motion

Use the motion shadcn and Base UI ship, tuned for the Studio, and turn all of it off under reduced motion. Panels animate width over about 200 ms; Details pushes over 220 ms on the quint ease; a staged preview keeps the previous frame on screen with a "Staging new preview" badge and swaps only on ready; popovers fade and zoom from their trigger; a walkthrough step fades in from 98% scale; Gallery cards stagger by 30 ms and lift 2 px on hover; phone drawers follow the finger.

## Status and modified state

Status reads from the preview runtime: Loading, Ready, Capture, No capture, Did not start (with Retry, which mounts the preview again), Showing previous settings (after a failed or timed-out change), Not designed, and Modified. Modified means a person changed product state in that runtime. Clicks and keys that change nothing do not count. It is a state, never a count of actions, and Reset clears it.

Edited · n properties is a separate status: the viewer changed n properties of the selected state. R resets product state and navigation and keeps property edits; Reset (n) in Properties clears them and leaves Modified alone. A property change applied in place does not mark the runtime modified: the frame client disarms its interaction window for each Studio change, so when a property change arrives within about 1.5 seconds of a person's interaction, a product change from that interaction that lands after it may not show Modified.

## Properties and saved states

Named states stay the unit of review. An input with `section: "properties"` is a component property: it applies only on its `surfaces`, appears under Details > Scenario > Properties, edits the selected state without a remount and shows as a difference from it. Controls are `switch`, `text` (`multiline`, `maxLength`, `shareable`), `number` (optional `min`, `max`, `step` and `presets`), `choice` (named options for values the frame owns; only the option ID crosses the boundary) and the existing `select`, `presets` and `range`. `curated` puts a row in the top group; `optional` leaves it unset, so nothing is sent, until Set; `readonly` with a `note` lists a property the Studio cannot edit, such as a function. Objects, arrays, slots and nodes are choices; there is no raw JSON editor.

A property ID must not be one of the Studio's own link keys: `view`, `scenario`, `theme`, `profile`, `size`, `tab`, `design`, `layout`, `frames`, `height`, `arrange`, `vp`, `sync`, `edited`, `module` and `section` (`RESERVED_LINK_KEYS` in `src/studio/input.ts`). A property with one of these IDs is rejected: it gets no row in Details, input normalization refuses every value for it, so it never reaches a link or the frame, and the console names it once. Rename it.

Values cross the frame as text, finite numbers or booleans. A frame whose client announces `live-values` applies them in place; an older frame, or one whose update fails, is remounted with them, and a value the product cannot mount keeps the previous preview with Showing previous settings until a good value mounts. Edits are kept per scenario in the viewer's browser. Links carry switch, select, number, range and choice values under the input ID, and text only when the input is `shareable`; other edited text adds `edited=local`, and the recipient sees the designed text with a note that the sender had local edits. Opening a link shows the link's state for its scenario, but does not erase the edits this browser stored for that scenario: they stay stored until the person edits that scenario there, and from then on the edits on screen are the ones kept.

Save as scenario writes a saved state `{ id, label, base, values }` (and an optional `description`) to `scenarios.json` (`studio-scenarios/1`) at the Studio root, a product file. Saved IDs start with `saved.`, which generated scenario IDs must not use, so a save never overwrites a generated scenario. A saved state joins the catalog under its surface, marked Saved, and renders its `base` scenario with the saved values; it can be saved again, renamed, duplicated and deleted. Save as and Save write the state as it now shows, as the values that differ from the base; an optional property the saved state sets can be cleared, and Save then leaves it out. Duplicate carries the current edits into the copy. The Studio skips a saved entry it cannot use: an ID that is not `saved.` plus lowercase letters, digits and hyphens, is a generated ID or is repeated; a label that is blank or over 80 characters; a base that is not a generated scenario; or values that are not an object. In an entry it keeps, a value that is not one of the base's properties, or not a valid saved value (text up to 4,000 characters, a finite number, or true or false), is dropped, and a description over 400 characters is dropped.

Only the dev server writes saved files. The Studio calls these endpoints only when it runs as a dev build (`import.meta.env.DEV`): a published, built Studio never requests them, so a host serving a production build receives none. It fetches them with relative URLs (`__studio/scenarios` and `__studio/layouts`), so they resolve against the Studio's own path: a Studio served under `/studio/` calls `/studio/__studio/scenarios`. The paths below are relative to the Studio's base in the same way. The contract, for a host other than Vite:

- `GET __studio/scenarios` answers 200 with the file as JSON, or `{ "schema": "studio-scenarios/1", "scenarios": [] }` when there is none or it cannot be read, with the file's revision in the `x-studio-revision` header. When the file exists but is not JSON (a merge conflict, say) it also answers `x-studio-unreadable: 1`, so a Studio never takes it for an empty list to save over.
- `POST` with a JSON body replaces the whole file. The server answers 403 when the request's `Origin` is missing or is not its own host, 415 when the body is not `application/json`, 413 above 256 KB, 400 for unreadable JSON, 422 with `problems` when `validateScenarios` in `src/studio/scenarios.ts` finds any, 500 with the reason when the file cannot be written, and 200 with `{ "ok": true }` once it is. Other methods get 405. Every answer is JSON with an `error` text on failure, except 409 (below).
- It writes a uniquely named temporary file and renames it over `scenarios.json`, so a reader never sees half a file.
- A change to the file must not reload or re-run the open Studio (Vite's plugin invalidates the module that bundles it and suppresses the hot update); the next page load reads it.
- Revisions: GET and a successful POST answer `x-studio-revision`, an opaque string the client never interprets (the dev server uses the SHA-256 of the stored bytes, and `empty` for a missing file). A POST may send `x-studio-expected-revision`; when it differs from the current revision the server writes nothing and answers 409 with `{ "ok": false, "error": { "code": "conflict", "reason": "<safe to show>", "recoverable": true }, "current": { "data": <the file, or null when it is not JSON>, "revision": "<current>" } }` and the header, the shape of a workspace operation conflict. The other answers (403, 415, 413, 400, 422) come before the revision check, and no other save through the same server can land between the check and the write. A POST without the header writes unconditionally, so a host without revisions keeps working, but its saves are then last writer wins.
- The Studio sends the revision it last read. Layouts carry it from the page's first load, so any save made elsewhere since is caught; until that first read returns, Save, Save as, Rename, Duplicate and Delete are disabled with "Loading layouts…". A file the server marks unreadable, or that is not a valid layouts or saved-states file, is never saved over: layout saves stay disabled with the reason until it is fixed and the Studio reloaded, and a state save is refused with the reason. Saved states read the file before each write and change only the entries the action concerns, writing every other entry back exactly as stored, including entries it skips; the revision catches a write that lands between that read and this write. A file the endpoint refuses (over 500 entries, 256 KB, or with an invalid entry) is reported, never trimmed.
- On a 409 the Studio loads the latest list, keeps the person's unsaved edits and says "changed elsewhere" in a toast; nothing was saved. The next Save writes their version against the new revision, knowingly replacing the other change; for layouts, Revert shows the other version. When the current file is not valid, the Studio keeps its list, takes only the revision and says so.

`__studio/layouts` follows the same contract, on the same dev-only and relative terms, for `layouts.json` with `validateLayouts`. A built Studio bundles both files and cannot save. The dev server's implementation is `scripts/saved-file.ts`, a shell file that a host can read as the reference.

## Check the shell

`npm run acceptance` in the starter builds the Studio five ways (the example product, a stress adapter with 1,000 scenarios, 1,000 tokens and a 40-step walkthrough with four broken steps, a capture-only adapter, the example with its synthetic workspace, also served without its operations host, and the example with that workspace and a synthetic component library; the stress adapter declares no properties, so it also measures a Studio without them), serves them locally and measures AC-01 to AC-68, WS-01 to WS-10 (with WS-05b and WS-06b) and LB-01 to LB-10 in headless Chromium. It needs Playwright (`npm i -D playwright` and `npx playwright install chromium`, or `PLAYWRIGHT_MODULE` pointing at an existing install). It prints each result, writes `acceptance-report.json` and exits non-zero on a failure. `ONLY=AC-03,AC-10` runs a subset. The stress, capture, workspace and library adapters build only when `VITE_STUDIO_ADAPTER` is set, and drop out of a normal build. The workspace build needs `example/workspace/` and the library build `example/library/`; the updater skips acceptance with the reason when either is missing.

Run it after any change to the shell, in the skill's starter; every shell release passes it there. Before connecting a product, run it unchanged in the new Studio to prove the shell. The script is a shell file, so a Studio does not edit it: it measures the shell with the example product, and the product's own checks belong in the product's verification (see [verification.md](verification.md)), which can reuse the criteria that need no stress data.
