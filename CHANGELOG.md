# Changelog

## 1.28.1 — 2026-10-22

- `metamodern-work-on-canvases` 0.4.1 lets several projects' viewers run side by side. Before, `canvas view` took the config's port and failed with "Port … is in use" when anything held it, and a browser that resolved `localhost` to `::1` could reach another project's server on that address while this one listened on `127.0.0.1` only. Now:
  - The viewer answers **`/_whoami`** with `{viewer: "metamodern-canvas", root, name}`.
  - **`findPort({projectRoot, from, tries})`** (exported from `lib/viewer-server.mjs`) probes `127.0.0.1` and `::1` on every candidate from the config's port on and returns the port where this project's viewer is already running (`{running: true}`), else the first port nothing holds, so a viewer pushed to a higher port is still found after the lower one frees.
  - **`canvas view`** says where this project's viewer already runs and exits 0 instead of starting a second; when another server holds the config's port it takes the next free one and says so. An explicit `--port` that is taken is still an error, and `--port 0` still asks the system for any port.
  - The viewer also listens on `::1` at the same port, so `localhost` reaches it whichever address the browser tries first; `close()` closes both. A failed bind on `::1` stops the start (the IPv4 side is closed) unless the system has no IPv6 loopback; with `--port 0` a port held on `::1` is retried.
  - Test: VW-09 (a port another server holds is passed over, `/_whoami`, finding a running viewer, another project's root never taking it for its own, a viewer above a freed port still found, and a port held on `::1` alone refused with the IPv4 side freed).

## 1.27.0 — 2026-10-21

- `metamodern-work-on-canvases` 0.4.0 makes the render check fast enough to run after every change. Before, `canvas render` loaded every board afresh in every theme variant, each in a new browser context, checked every board on every run, and then waited about 30 s for Chromium to shut down; a builder change took two builds and two renders before new heights applied. On AUTOSTAK's design project (2,049 boards, 5,934 renders), a check with nothing changed now takes about 2 s instead of a full run (31 min under load), rebuilding one canvas with a changed board takes 11 s instead of 84 s, a cold canvas renders 1.8 to 2.6 times faster, and a kit sync that changes one component re-checks about 109 boards in about 1 min when the kit declares part hashes (1,245 boards without them).
  - **Only what changed.** Each board is keyed by everything its render depends on: the content of every file it loaded (recorded from its own requests: the board, imported boards, styles, pictures, fonts, the runtime, the skin and the kit), its size, kind and kit choice, its variants, `canvas.config.json`, the package and Chromium versions, and how variants are drawn. A board whose key is unchanged keeps its result and pictures (`"reused": true` in the report), a failing one included, since the same inputs fail the same way; a board whose failure can pass by itself (a timeout, a failed navigation or request), `--board` boards and `--force` runs are always checked. Keys live in `<out>/<canvas>/cache.json` (`canvas-render-cache/1`); the report gains `checked` and `reused`.
  - **Kit part hashes.** `kit.json` may declare `parts: {shared, components: {<path>: hash}}` (contract 3, optional; `validateKitManifest` checks it). A board that mounts such a kit is keyed by `shared` and the parts it names (`<Ns>.Button`, `<Ns>.sample.x`, or `A.x` after `const A = window.<Ns>;`), so a kit sync re-checks only the boards that use what changed; a board that reaches the kit any other way is keyed by the whole kit. `partHashes({metafile, root, shared, components})` computes them from a bundler's module graph.
  - **Variants in place.** Each board loads once, in its own context (storage still never crosses boards), and is switched to each further variant through the runtime's `props` and `render()`, as the viewer's controls do; the check waits for mounts and frames and finishes the CSS transitions the switch started. Problems from the load go with the first variant, problems after a switch with that variant. `"reload": true` in a canvas's `tools/render.json`, or `--reload-variants`, loads each variant afresh as before. On AUTOSTAK's design project, of 2,157 pictures of boards unchanged between a 0.3.0 and a 0.4.0 run, 1,750 are identical, 366 differ by anti-aliasing (64 pixels or fewer), and the other 41 are all motion or loading boards, whose first, freshly loaded variant differs between runs too.
  - **`canvas build [--canvas <id> ...]`** runs each canvas's `tools/build.mjs`, checks what changed, and when measured heights changed builds and checks again (up to three rounds), so new heights apply in one command.
  - **`canvas render --watch`** keeps the browser open and re-checks the canvases whose files, skin or kit changed, using the viewer's watcher.
  - **Faster shutdown.** The browser runs as a Playwright browser server the check connects to and kills at the end; `browser.close()` could take 30 s on macOS (the package's RC-01 and RC-05 tests took about 32 s each for that).
  - Parallel boards default to all processors but two, from 2 to 8 (was half): 8 boards finished lab-selection in 27.5 s against 33.3 s with 5 on a loaded machine.
  - `createRenderSession()`, `watchRender()`, `buildAndCheck()`, `summary()` and the key helpers (`boardInputs`, `boardKey`, `kitReferences`, `partFor`, `fileHasher`, `readKitParts`) are exported from `render-check.mjs`; `switchProps()` from `lib/check-board.mjs`; `watchProject()` from `lib/viewer-server.mjs`. Tests: RF-01 to RF-11 (keys, kit references and aliases, part hashes, inputs, skipping and re-checking, kit parts, in-place and reload variants, `canvas build` with heights, the watch), and RC-04 now loads half its boards dark first so a shared context would still fail it.

## 1.26.0 — 2026-10-21

- `metamodern-work-on-canvases` 0.3.0 records exploration rounds. Before, an exploration canvas had no record of rounds: when the decision-maker commented and the options were redrawn, the earlier options were lost or piled up on Directions. Now Directions holds the current round only, and every earlier round is kept as the decision-maker saw it, with their words:
  - **`canvas explore round <id> --said "<the decision-maker's words>" [--learned text] [--board <file> ...] [--renders <dir>] [--date YYYY-MM-DD]`** (`roundExploration`) keeps the options on Directions (every board on the page but its intro and row banners, or the `--board` subset) as the picture of their last render at `project/assets/round-<n>/<stem>.png`, with their source at `source/round-<n>/<file>`, and adds `{n, date, said, learned, boards: [{file, title, image, w, h, source}]}` to `rounds` in `tools/explore.json`, whose `round` (1 for a new canvas) moves on. It uses the same render lookup as `canvas review archive`, and a render that failed is kept as it was seen. Before writing anything it refuses an empty `--said`, a board that changed since its render (the picture would not be what the decision-maker saw), a board that is not on Directions, a round whose boards and sources are all the same as the last round's (a command run twice), and a decided canvas.
  - **`explorationSpec(canvasDir, {directions, lead, precedent})`** gives an exploration's builder script the template's pages from `tools/explore.json`: Start here with the question, the state and the rounds, plus an optional Precedent board of `{title, href, note}` links (each `href` an http(s) link or a viewer path, checked as `ws.facts` links are); a Directions intro naming the current round and quoting the last round's `said` and `learned`, then the builder's rows or boards; Lead; and Archive, a row per round, newest first, of picture boards `R<n>_<stem>.dc.html` drawn with the archive canvas's picture board. Round pictures are drawn on every build, so they stay on Archive after their options leave Directions, and a second build writes nothing. `canvas explore create` builds through it, and `canvas explore decide` keeps the rounds and lists them on the decided Start here.
  - `review-sets.mjs` exports `renders`, `byTheme` and `pictureBoard` (the archive's picture board shell) for this; the archive canvas's output is unchanged. An `explore.json` written by 0.2.0, without `round` or `rounds`, reads as round 1.
  - The method gains Rounds under Exploring (Directions holds the current round only; `canvas explore round` when the decision-maker has commented and the next round starts; the builder then draws it) and Cleaning up after a decision (decide freezes the canvas with every round on Archive and moves it to the decided group; after the lead goes live, `canvas review archive` keeps the replaced boards and the decision log names the exploration canvas). Tests: RS-12 (a round's pictures, words and source; stale renders, a repeated round, a decided canvas and empty words refused with nothing written; the command line) and RS-13 (the template's pages through `explorationSpec`, rounds newest first surviving rebuilds after their options leave Directions, a second build writing nothing, precedent links and their check, and the decided Start here).

The home page refreshes when an icon file is added or removed. Tests: CF-09 (the new fields), BB-08 (a bare board and its facts), VW-08 (the index's about line, icon, facts and group names) and VW-17 (the home page's headings, icons, tones, whole-card links and the card's keyboard focus ring, banners on an all-pinned page and beside a live board, and the panel's facts) in headless Chromium.

## 1.24.1 — 2026-10-20

- `metamodern-work-on-canvases` 0.1.1 fixes the motion controls for pseudo-element motion. A CSS transition or animation on `::before`, `::after` or `::marker` that started after the rate was set ran at full speed: the runtime applied the rate to new animations with `getAnimations()` on the event's target, which leaves out the target's pseudo-elements, so at a quarter a switch's track slowed while its thumb's fade did not (a page-wide pause still caught them, since it lists the whole document). The runtime (0.0.4) now takes the element's own animations and its pseudo-elements' with `{ subtree: true }` (never its descendants', which keep their own rates), falling back to the document's animations on that element, so new pseudo-element motion starts at the board's rate, slows to a quarter and stays still at 0. A CSS transition or animation is announced one update after it was created, and an animation with a delay only when its delay ends, so it had already run at full speed (6 to 30 ms of a 400 ms run when paused, which showed as a small drift after pausing, and a whole delay at a quarter); while the rate is not 1 the runtime now also adopts new animations on every frame, and adopts each once: if it was created after the last rate change, the time it ran at full speed is scaled to the rate (to its start while paused), then the rate is set. Replay at full speed also resets the speed of animations that stay on the board. Pausing now holds an animation at once: the runtime sets its rate to 0 (which keeps its current time) before pausing it, because Chrome commits a pause only at the next update and an animation whose start was still resolving ran on for up to about 70 ms after the board paused; the direction is kept for when the board plays again. The board's rate also keeps an animation's direction, so one a script reversed stays reversed. A runtime test times a `::before` transition at a quarter (about 4 times as long), holds an `::after` animation and a transition started while paused at their start, checks the first frame at a quarter, times a delayed animation at a quarter, and checks that a parent's transition leaves a child at its own speed and a reversed child reversed.
- The render check no longer fails boards that hold a script-free frame. It marked the runtime ready through a Playwright init script, which Playwright injects into every frame; in a sandboxed `srcdoc` frame without `allow-scripts` (an email preview) Chromium refused it and logged "Blocked script execution in 'about:srcdoc'", so every such board failed although it was clean. The check now reads the runtime's `ready` promise from the main frame after load and injects nothing into frames. Nothing is filtered: an error a frame's own script logs still fails the board, and a test covers both.
- `canvas comments`: a comment's `link` (in `list`, `wait` and `take`) now points at the viewer that recorded the comment, on its own port, taken from the comment's recorded `url`; the config's port is used only when a comment has none. Before, every link used the config's default port, so an agent following a link from a viewer on another port reached no viewer.
- `canvas comments take` names the innermost harness: Codex's own session variables (`CODEX_THREAD_ID`, `CODEX_SESSION_ID`) are checked before Claude Code's, so a Codex session started from inside Claude Code (which inherits `CLAUDECODE`) is recorded as `codex/<session>`. Other `CODEX_*` variables, such as `CODEX_HOME` or a Claude Code plugin's `CODEX_COMPANION_SESSION_ID`, leave a Claude Code session named as one.

## 1.23.0 — 2026-10-20

- `metamodern-work-on-canvases` 0.0.4 adds comments (contract 4, `references/comments.md`). In the viewer, `C` turns comment mode on: click any element on any board at any zoom (boards run live from 10% zoom while commenting), drag a box for an area, or comment on the selected board (Shift C); Enter posts and Esc cancels. Each comment is a numbered pin on its board that follows pan and zoom, and a thread in the new Comments tab, listed by canvas and board, with Open, Resolved and All; clicking one flies to its pin. **Send all to agent** bundles every open comment into one batch. Comments are files in the project, one per comment at `comments/<canvas>/<id>.json` in Agentation's annotation format (AFS 1.1) with the package's facts under `canvas` (canvas, page, board, kind, stable label, rect, kit, the board's values, moved, batch, the element's text); batches are `comments/batches/<id>.json`; every write is atomic under a short lock. States: open (`pending`), addressed (`acknowledged`, by the agent), resolved (only by a person in the viewer), reopened by a person's reply. The agent's command line, `canvas comments list | wait | take | reply | done` (Node built-ins, JSON out), is the same on every harness; `wait` delivers a sent batch to a listening session well within a second. The runtime (0.0.3) implements `canvas:pick`, `canvas:picked`, `canvas:locate` and `canvas:located`: labels from `data-canvas-id`, `data-kit-component` with its position, `data-test`/`data-testid` or a CSS path, picking on pointer release, and re-attachment only on unambiguous evidence (locate answers carry the question's request number; long words keep a digest of the whole text): the element's own unique label, else its own words when no other element of its tag has them (inside a repeated structure, checked against its row's evidence, so words never follow into another or a new row), else an identity among look-alikes (a stable anchor, a shape hash so differently drawn items differ while new class names and generated ids do not, up to three levels of own and other tokens that reject any row holding another row's words, and its place among identical items only while their number is unchanged); after a board loads, comments re-attach (the pin follows the element) or show as moved at their last place, and are never lost. Moved is preferred to a doubtful attachment, and places are written only while the board shows the comment's own values. The viewer server answers same-origin JSON POSTs for comments only and sends a `comments` event when the files change. A spike before the build: 64 of 64 scripted picks on the intended element across zoom 0.25, 0.5, 1 and 2 with pan offsets, 130 of 130 re-attached after regeneration, 11 of 11 removed elements shown as moved, none wrong or lost; with cases added over four reviews (textless images, shared "Edit" labels, identical and differently drawn icons, ranked and re-sorted rows, edited cells, rows added and removed, words moving between rows and into new rows, rows taking another row's words, nested cards, regenerated ids, status badges in table cells and cell wrappers, long texts alike for 200 characters: 639 comments in all), 567 re-attached to the same element, 70 shown as moved as designed, 2 accepted as indistinguishable by design, none false-moved and none on a neighbour; a textless icon on a 601-row board is found in about 4.5 ms.
