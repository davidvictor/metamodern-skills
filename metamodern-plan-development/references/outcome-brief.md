# Outcome brief

Use the existing task record. These are useful questions, not a new required schema. Omit facts already clear from the request or linked project record.

| Question | What to capture |
| --- | --- |
| What changes for the user? | Observable outcome and one or two acceptance examples |
| What must survive? | Supported behavior, values, access boundaries and accepted obligations |
| What may we replace? | Authorized visual, structural or API changes; deliberate unsupported cases |
| Where do we stop? | Requested endpoint and separately authorized external actions |
| What proves it works? | Focused checks, required integrated checks and suitable environment |
| What belongs to the user? | Only unresolved decisions with a material consequence |
| What happens next? | Owner, coherent delivery batch, relevant source revision and next action |

The project's required ownership, branch, resource, model and recovery records still apply. Link them rather than copying them here. Do not add mandatory timing fields, forms, dashboards or a workflow engine to answer these questions.

The brief is agent-authored. The user can speak in shorthand, describe several connected changes or steer an ongoing task. Reflect the intended result and meaningful assumptions at their level of detail, resolve routine technical choices, and ask only about an unresolved material meaning. Clear readback is not a demand for approval or another form to fill out.

## Human direction and autonomy

A clear build request authorizes bounded implementation and reversible choices within its scope. It does not authorize unrelated backlog work or expand permission to merge, publish, deploy, spend or message others. Apply the current request and standing authority to each endpoint.

Use collaborative decisions only where the user contributes something the agent cannot responsibly infer. Offer a small number of concrete options with their consequences. Avoid interviews about routine implementation choices. When the user steers ongoing work, update the outcome and affected assumptions; retain valid evidence and independent progress.

Urgency changes prioritization and how much reversible polish is deferred. It does not prove a behavior works or erase access, data or recovery obligations. Read the project's actual audience and environment; do not infer that every project is pre-launch.

For larger work, plan sequential worktrees with a quality cadence: a focused baseline for the affected surface, focused checks during implementation, rendered/interaction evidence before final validation when relevant, required integrated checks and independent review at each delivery boundary, and affected integration checks before dependent work proceeds. Reuse applicable evidence; never use batching to defer required validation until several risky changes accumulate.

## Representative examples

For an authorized UI-library replacement, the brief might preserve submitted values, validation, keyboard operation, focus return and public imports while allowing component anatomy and visual conventions to change. Migrate one real form and one overlay first. Use component checks during edits, inspect representative mobile/desktop rendering, then run the supported application journeys at integration. Obsolete selectors are test repair; broken values or inaccessible controls are product defects.

For an invoice-calculation correction, preserve rounding, authorization and persisted totals. Reproduce the failing calculation, add a regression at that boundary and verify affected callers. A frontend file extension does not lower the consequence of a financial error. Merge and production rollout follow the project's existing authority.
