# Engineering foundation

## Default operating model

Start with one implementation owner and one integration owner, often the same person. Add a bounded specialist only for a concrete risk or useful independent work with a stable interface and separate writable files/resources. Use one integrated independent review for substantive implementation, grouped correction, and targeted re-review. Available roles are optional; do not require a task graph, hooks, sibling repository, or specialist suite.

Make reversible implementation decisions within authorized scope. The user owns product meaning, consequential ownership or compatibility choices, external obligations, spending, and destructive effects. Define the delivery endpoint: ordinary authorized development may reach its agreed checks, review, and PR path; merge, deployment, and publication follow recorded authority.

Authorized engineering setup uses `metamodern-configure-engineering` to install or reconcile the shared profile and portable testing policy. The canonical package is [Configure Engineering](https://github.com/davidvictor/metamodern-skills/tree/main/metamodern-configure-engineering). Preserve project decisions and native overrides. File configuration checks, verified model availability, native discovery, and a successful provider turn are distinct evidence states. Inspect-only initiation does not install the profile.

## Code and verification

Verify the actual checkout, branch/worktree, instructions, source revision, runtime, resources, and command effects when starting or resuming. A worktree does not isolate services or data. Keep repository-wide checks read-only in dirty workspaces, scope fixers to owned files, and preserve unrelated work.

Use the installed `docs/engineering/testing-policy.md` alongside current project obligations. Choose the lowest trustworthy proof layer for the changed behavior. Use targeted test-first work for meaningful access, durable state, money, destruction, idempotency, stable shared contracts, and escaped defects; cover success, failure, and recovery in proportion to risk. Test allowed and denied cases where authority changes. Use browser/device evidence where lower layers cannot prove a claim. Exploration may use manual/static proof with a stated reason and promotion follow-up. Keep provisional choices changeable with intent and replace obsolete assertions while preserving actual obligations. Do not impose a coverage quota or test incidental implementation.

Inspect upstream extension points and every affected shared consumer before changing shared code. Use project-local skills only for substantial project behavior, with a unique project namespace; reference shared capabilities by canonical name and do not create same-name collisions. Core checks must work without sibling repositories or optional agent hooks.

## Resource and recovery discipline

Record task-owned mutable resources and their cleanup owner. Isolate or serialize concurrent mutable work. Stop, reset, delete, provision, or contact external systems only under current authority and after target verification. After two unsuccessful corrections of the same cause without new evidence, change diagnosis or narrow the task instead of adding retries or speculative guards. Runtime budgets and required commands come from the project, not a universal profile.
