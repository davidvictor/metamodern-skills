# Engineering interview

Inspect current sources, code, authority, checkout, capabilities, local resources, and runnable commands before asking. Reuse decided values and label each item as a discovered fact, reversible default, user-owned judgment, or deferred decision.

Ask one small material group at a time, recommend reversible defaults with reasons, and stop when the first task is executable.

1. **Outcome and acceptance.** What user or technical outcome is authorized now? Capture acceptance examples, exclusions, source authority, and delivery endpoint.
2. **Consequential constraints.** Ask only about access, privacy, compatibility, data integrity, external obligations, spending, or irreversible effects that the named task can change.
3. **Foundation.** Recommend the smallest foundation that supports the task. Branch only when relevant: account/tenancy access, payments, durable or AI work, mobile platform/offline capability, website editing, or compatibility with an existing system.
4. **Operating authority.** Resolve writable scope, implementation owner, shared-code/upstream boundaries, dependency owners, review/check expectations, and actions authorized on the delivery path.
5. **Task dependencies.** Confirm the actual checkout, required runtime/resources, required tool access, and a recovery or discovery action for each missing capability.

Do not ask for a full product or design intake. Do not request credentials or secret values. A missing provider, tool, or decision blocks only its dependent action or claim; continue useful inspection and independent preparation.
