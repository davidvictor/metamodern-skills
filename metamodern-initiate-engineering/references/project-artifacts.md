# Project artifacts and ownership

Use the smallest artifact set that makes the named task portable and reviewable. Project Preparation creates or merges the portable core: `PROJECT.md`, `REFERENCES.md`, and `AGENTS.md`. Initiation supplies engineering facts to those owners; it does not write substitute product, brand, or design documents.

Keep requirements in their declared product source. Git owns technical decisions and code. GitHub owns engineering delivery evidence. Bonsai owns business, project, commercial, invoice, and revenue facts. Existing design and editable visual sources retain their owners. Source snapshots, plans, and receipts are evidence, not competing status systems.

Use an existing README or engineering guide plus one issue or work packet where sufficient. Add an ADR only for a consequential alternative, including its status and reconsideration condition. Keep `AGENTS.md` concise: read project/product authority first, then local instructions, the named task/work packet, actual runtime commands, and relevant shared-code or delivery boundaries. Route external tools through their current official or vendor guidance rather than copied manuals.

Create a uniquely named project-local development skill only when local behavior needs reusable routing; do not copy a shared skill into the project. Its content is the actual local commands and prerequisites, relevant extension points and source boundaries, focused checks/review, and delivery permission path. Reuse existing project documents rather than creating parallel guides.

When portable context is missing, or required engineering fields are stale or absent, initiate Project Preparation with the known decisions and a portable-core-only merge request. It preserves unrelated and upstream guidance, returns directly to this workflow, and must not initiate engineering or bootstrap again.
