# Metamodern Bootstrap App

## Purpose

Prepare one current MakerKit Turbo checkout for a named task. This skill is MakerKit-specific despite its broad name. It is independently usable and does not provision hosted services, publish a site, or replace product, brand, design, or portable-project ownership.

## Establish the run boundary

Identify the checkout, source/ref and license access, task outcome, whether it is a fresh kit or continuation, branch/worktree, instructions, dirty paths, remotes, installed runtime, and owned local resources. Read the source's current instructions and manifests before deciding a change.

Read [MakerKit baseline](references/makerkit-baseline.md). It is an inspected baseline, not a pinned starter release. Refresh it against the selected checkout before relying on a source touchpoint, command, version, route, environment variable, or configuration field. Missing source access blocks only the dependent change or claim.

For a non-MakerKit application, report the mismatch and route to the appropriate preparation or project capability. Do not convert it automatically.

## Reuse known decisions and ask only for gaps

Consume supplied and established product, source, and authority decisions. Do not repeat an answered interview or conduct a full design interview. Read [Interview](references/interview.md) and ask only unresolved decisions required for the named task, in dependency order.

Keep display name, technical slug, repository identity, and domain distinct. Reuse supplied names; derive reversible technical names; do not broadly rename upstream tables, packages, or legal/operator details.

Project Preparation owns `PROJECT.md`, `REFERENCES.md`, and `AGENTS.md`. Product, brand, and design capabilities own their corresponding artifacts. This skill records a scoped bootstrap map and evidence rather than authoring competing artifacts. In standalone or composed use, invoke Project Preparation only when the portable core is missing. Give that caller the known decisions and a portable-core-only scope; it must not dispatch engineering initiation or bootstrap again.

## Prepare deliberately

Read [Starter preparation](references/starter-preparation.md). Produce a reviewable keep, adapt, hide, remove, or defer ledger before changing starter surfaces. Prefer configuration and supported extension points. Preserve authentication, account/RLS, error, localization, update, and necessary upstream paths unless a supported product decision changes them.

Derive a local stack identity and noncolliding ports from actual repository configuration, current port use, and resource ownership. Record uncertainty because a probe alone cannot prove future collision freedom. Use project-local CLI commands and ignored local overrides where needed; do not print environment values. Reconcile every active development and test consumer before claiming isolation. Provide synthetic local fixtures and callback/passkey origin values only for the owned local identity. Never reset or stop another project's stack; do not run a destructive reset without specific authorization.

This package does not provision hosted Supabase, OAuth, billing, email, CMS, deployment, payment providers, or production configuration by default. Perform them only when the current session or standing recorded authority covers the specific action. Their code or flags do not prove provider setup.

## Verify and hand off

Read [Verification and handoff](references/verification-and-handoff.md). Select path-targeted checks for the changed surfaces. Establish installation with the lockfile, the `packageManager`-pinned pnpm, and a compatible Node runtime; ensure child lifecycle commands resolve the same pinned pnpm rather than a global version. Do not run all generic risky scripts as an initial baseline.

Report the exact source revision, decisions, retained and changed surfaces, local resource ownership, checks and results, baseline failures, dependencies, and first development handoff. State readiness as a named-slice scoped runtime result. Local checks or a local stack do not establish repository delivery, deployment, or live verification.
