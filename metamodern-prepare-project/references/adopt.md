# Adopt

Use Adopt when implementation, assets, documents, decisions, skills, or active work already exist.

## Read-only inventory

Inspect:

- Repository, project, application, and worktree boundaries.
- Git status, branch, history, and remotes.
- Existing instructions and skills.
- Documentation and working files.
- Code, configuration, assets, routes, and implementation.
- Product and visual maturity.
- Durable external links and connected records.
- Review and published surfaces when accessible.
- Current planning, feedback, meetings, and decisions.

Treat file age, Git tracking, implementation, and document titles as evidence rather than automatic authority.

## Workspace map

Return:

- Existing project truth.
- Existing artifacts and their supported roles.
- Incumbent product and visual authority.
- Conflicts, stale material, and unresolved decisions.
- Missing portable artifacts.
- Available shared and project skills.
- Exact proposed local additions or updates.
- Existing work that remains untouched.

## Reconcile safely

Create missing `PROJECT.md`, `REFERENCES.md`, and `AGENTS.md`. Merge supported material into existing core artifacts without overwriting unrelated guidance.

Before writing, compare the exact change set with the affected modified and untracked paths. When a proposed core artifact already has dirty user work or the write overlaps another modified target, report that overlap and ask one focused reconciliation question. Unrelated dirty work does not block adoption.

Route capability artifacts to their owners:

- Existing user-facing interface: preserve it as implementation evidence. Read [Impeccable interface foundation](impeccable-interface-foundation.md) and verify the derived local runtime, project hook, and persistent runtime trust only when the current request authorizes interface-production setup or implementation.
- Existing frontend without `PRODUCT.md`: when interface-production setup or implementation is currently authorized, use Impeccable init with repository evidence and focused human confirmation; otherwise record the missing artifact without initializing it.
- Existing visual implementation without `DESIGN.md`: when interface-production setup or implementation is currently authorized, use Impeccable document mode after comparing implementation evidence with accepted brand authority; otherwise record the missing artifact without creating it.
- Existing identity evidence without accepted `BRAND.md`: use Brand Development rather than inferring a Brand System solely from appearance.

Preserve current files and link them as evidence. Cleanup, movement, deletion, staging, committing, merging, deployment, publication, and client decisions remain separate actions.

When a durable link cannot be opened, preserve its supplied role and access requirement but leave Last verified without a current date. Never convert the existence of a URL into a current-state claim.

## Engineering continuation

When engineering setup is requested, let `metamodern-initiate-engineering` reconcile existing requirements, decisions, checks, environment evidence, and the next meaningful task. Preserve upstream and nested instructions, project-local skills, current source authority, and working delivery conventions. A bootstrap-specific request uses `metamodern-bootstrap-app` without requiring full initiation. Pass earlier decisions and stop only the dependent step for unresolved authority or unavailable access.

A portable-core-only delegation returns after the narrow core merge. It does not restart engineering, bootstrap, interface setup, or product intake. Historical runtime receipts are not fresh runtime proof; verify actual resources before using them.
