# Metamodern Proposal Workflow

## Artifact decision

| Situation | Artifact |
| --- | --- |
| Small addition to active work | Written budget confirmation in the project's record system |
| New client or substantial engagement | Full proposal in the project's destination system or approved template |
| Retainer or recurring service | Full proposal with clear start, billing, change, and termination terms |
| Material change to accepted scope | Change proposal or new bounded work order |
| Opaque inherited system | Paid, capped discovery or a fixed scope with explicit stop conditions |

## Evidence order

1. The user's current instruction and supplied evidence
2. The project's approved commercial and proposal policy
3. Current client, project, proposal, invoice, and time history in the applicable record system
4. Relevant meeting notes, then transcripts only when notes lack required detail
5. Current technical or public-system inspection when it changes scope
6. Comparable completed work and historical proposal evidence, clearly labeled

Use current sources over memory. A historical proposal never proves acceptance or current price.

## Private scope contract

Produce a source-aware internal record containing:

- Client, engagement, commercial shape, and status
- Desired outcome and objective completion criteria
- Scope, deliverables, exclusions, client responsibilities, and dependencies
- Uncertainty class and stop or change conditions
- Planned human-active effort including meetings, coordination, agent review, QA, and delivery
- Agent activity and material tool or third-party costs as separate inputs
- Proposed fee, approved authority, planned effective revenue, and target variance
- Source pointers for material facts and client commitments
- Destination-system entry configuration and manual boundary

Track actual effective revenue only after the fee and human hours cover the same completed work boundary.

## Client proposal contract

Use this order, omitting only sections that genuinely do not apply:

1. Executive Summary or tailored context
2. Objectives
3. Scope of Work
4. Deliverables
5. Timeline, revisions, or phases
6. Assumptions
7. Client Responsibilities
8. Out of Scope
9. Native fee structure required by the destination system, when applicable
10. Terms and change control
11. Next Steps
12. Approved closing section, when the project's template requires one

Client copy includes concrete scope caps, acceptance criteria, dependencies, exclusions, change triggers, payment terms, ownership, and any approved efficiency statement when relevant.

Client copy excludes internal rates or targets, planned human ceilings, prompts, agent runtime, compute traces, private negotiation limits, raw meeting material, and unsupported status claims.

## Native fee structure contract

When the destination system provides a native fee component, every full proposal must map pricing directly to it:

1. Package title
2. Package description
3. One or more item rows, each with item name, optional item description, quantity, price, and total
4. Tax
5. Currency
6. Payment requirement

The destination system may calculate subtotal, tax amount, and total. Return the completed field values as the proposal's entry map. Do not replace a required native structure with narrative investment copy or a generic two-column fee table.

Mirror the verified destination editor's presentation. Where it uses item rows, include the item name and optional description, quantity, price, and total; package title and description appear where the editor requires them.

Use a separate option only for genuine alternative packages authorized by the user. Additive phases, deliverables, or recurring services that are accepted together remain item rows inside the same authorized package.

## Approved close contract

When an approved proposal template requires a close, use its exact approved section. Do not shorten, paraphrase, tailor, or replace it unless the designated approver approves new copy and the project's brand or proposal authority is updated first. Do not add a generic agency biography or positioning section when no approved close exists.

## Setup-to-recurring transition

Determine proposal count and activation from current approved commercial terms and the user's current instruction.

- When acceptance authorizes the complete engagement, use one proposal with separate one-time and recurring native fee items. State the objective condition that completes setup, starts recurring service, and begins recurring billing.
- When setup and recurring service require independent buying decisions or later written activation, use separate artifacts and state that accepting setup does not activate recurring service.
- In either structure, keep setup deliverables, recurring responsibilities, and out-of-scope work distinct.

Never hardcode either structure as the Metamodern default. The current client-specific authority controls.

## Status and manual destination-system boundary

- Use `Draft` or `Unsent` for local artifacts.
- Use `Unverified` when a live status cannot be read.
- Never infer `Sent`, `Accepted`, `Signed`, `Invoiced`, `Paid`, `Complete`, or `Active` from a file.
- Recheck the live destination-system capability before entry.
- If proposal creation remains unavailable through an integration, provide finished copy and the native fee configuration for manual entry.
- Read the manually created proposal visually, preserve its direct link, and report its visible status exactly.

## Common failures

- Returning a plan or implementation brief instead of finished proposal artifacts
- Pricing the risk of an inherited system before inspecting its real state
- Imposing a one-proposal or multiple-proposal structure instead of following current Approved terms
- Returning a prose fee section or generic price table that does not map directly to required native fields
- Copying fees, hours, deposits, or terms from an unsent historical proposal
- Exposing the internal effective-revenue target or human ceiling to the client
- Treating agent runtime as human billable time
- Using generic biography or public positioning that is not currently approved
- Shortening, paraphrasing, tailoring, or replacing an approved required closing section
- Creating, sending, or assigning status without the user's instruction and live verification

## Minimal example

For an inherited website with setup followed by ongoing maintenance:

- Inspect the public site, hosting responsibilities, access state, and relevant record history.
- Read the current approved client terms to determine whether acceptance covers both phases or each requires separate activation.
- Produce the corresponding artifact structure with an explicit recurring-service and billing start condition.
- Keep internal economics private.
- Enter only the authorized proposal record or records in the destination system and read them back before treating them as final.
